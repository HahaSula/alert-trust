## 判讀

1. **模型給的是平均，實際結果取決於固定的相位。**Scrape 與 evaluation 的相位在一次執行中是固定的。S = 120s、`evaluation_interval` 30s 時，每個 scrape 週期只有 4 個固定的 evaluation 時間點，空結果只會是 25% 或 50%，不是平均的 33%。`s120-d100-r5m` 的 50–56% 就是運氣差的相位，也就是圖 3 的「成立、成立、空、空」。兩個版本都從未 firing，pending 重新開始 10–11 次。
2. **留有餘裕的組合全部成立。**`s120-d100-r5m-o2m`、`s120-d100-r10m-o2m`、`s60-d40-r3m`、`s30-d25-r2m` 在兩個版本都是 0% 空結果，而且都有 firing。也就是 `O ≥ d` 或 `R ≥ 3I` 時，相位與抖動都不影響結果。
3. **視窗剛好等於 2S 很脆弱，加 offset 也一樣。**`s60-d5-r2m`（d 只有 5s）有 19–22% 空結果，`s60-d40-r2m-o1m`（offset 已大於 d）也有約 20%。Scrape 時間戳有毫秒級的抖動，視窗邊界上的那一點時有時無。這支持契約裡 `R ≥ (2 + k) × I` 至少取 k = 1。
4. **3.x 的左開區間量得到。**`s120-d60-r5m` 在 2.51.2 只有 3% 空結果、482s 開始 firing；在 3.13.5 有 25% 空結果、從未 firing。d 剛好讓最舊那一點落在視窗左邊界，2.x 的閉區間算進去，3.x 不算。
5. **單次執行的雜訊。**`s30-d25-r1m` 在 3.13.5 的空結果是 50%，卻在 250s 時 firing 過一次；`s60-d40-r2m` 在兩個版本分別是 50% 與 88%。相位在執行之間會不同，這些格子要看成「會不會穩定成立」，不要看單一數字。

## 限制

- 用 HTTP 延遲模擬 scrape 耗時，只能做 `d < S`；tick 被丟掉（`d > S`）的情況要用真正的大 target。
- 每組只跑一次，所以相位造成的差異只觀察到一種情況。
