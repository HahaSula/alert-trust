## 摘要
環境：mariadb:11.4（11.4.13）與 mysql:8.4.7 各一組 primary + async replica（GTID），每個節點一台 prom/mysqld-exporter:v0.21.0，
prom/prometheus:v3.13.5 載入 rules/targets/mysql.yml，scrape 5s。exporter 帳號：PROCESS、REPLICATION CLIENT、SELECT（MariaDB 加 SLAVE MONITOR），MAX_USER_CONNECTIONS 3。
ALERTS 多半是 pending（規則的 for 比情境長），pending 代表運算式成立。

- s1：MariaDB 的 perf_schema.replication_applier_status_by_worker collector 失敗（表不存在）。MariaDB performance_schema=0，sys.user_summary 回報成功但沒有 series。
  MariaDB 沒有 super_read_only；MySQL 沒有 Innodb_history_list_length、Innodb_deadlocks 這兩個 status。沒有交易時 innodb_trx 沒有任何 series。
  沒開 Galera 的 MariaDB：wsrep_ready=0、wsrep_on=0。MariaDB 內建 semi-sync，所以 rpl_semi_sync_master_status=0 一直存在；MySQL 沒裝 plugin 時沒有這組 metric。
  exporter 自己用掉 MAX_USER_CONNECTIONS 3 的 2 條（sys current_connections / max_user_connections = 0.67，s1 之後另外手動查詢）。
- s2：長交易 11–16 秒可在 innodb_trx_oldest_transaction_age_seconds{state} 看到（RUNNING 與 LOCK WAIT 分開）；row_lock_current_waits=1。
  consistent snapshot 擋住 purge 時 history 到 414（MariaDB）/434（MySQL）；交易結束後 MariaDB 降到 1，MySQL 仍是 500。
  SLEEP(30) 也算 slow query（long_query_time 預設 10s），MySQLSlowQueries 會響。
- s3：一次 deadlock：MariaDB 的 global_status_innodb_deadlocks 與 innodb_metrics 都 +1；metric 名稱 MariaDB 是 ..._lock_deadlocks，MySQL 是 ..._lock_deadlocks_total。
- s4a：replica SQL thread 等 metadata lock：Seconds_Behind 21/28 秒、heartbeat 21/28 秒一致；processlist state=waiting_for_table_metadata_lock 看得到。
- s4b：IO thread 停 25 秒：io_running=0，Seconds_Behind 兩邊都消失（NULL），heartbeat 延遲 27–29 秒。MySQLReplicationNotRunning pending。
- s4c：primary 的 heartbeat 寫入停：四台 heartbeat 都 25–28 秒，Seconds_Behind 都是 0。heartbeat 規則在每台都會響，代表寫入程式停了。
- s5a：STOP SQL_THREAD：sql_running=0、Seconds_Behind 消失、heartbeat 持續變大。
- s5b：衝突寫入：last_sql_errno=1062、sql_running=0，MySQLReplicationError 與 NotRunning 同時 pending。
