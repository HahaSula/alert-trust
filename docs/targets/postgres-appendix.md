# 附錄：從資料庫原始碼到 metric（PostgreSQL）

[主頁](postgres.md)列出每個訊號該看哪個 metric。這頁回答另一個問題：**這個 metric 真的是從那個 view 欄位或函式來的嗎？值是 NULL 時會怎樣？**每個訊號都追完整條鏈：

1. **資料庫端**：值在哪裡產生。PostgreSQL 16.15（`REL_16_15`）、17.11（`REL_17_11`）原始碼中定義 view 欄位、填值或遞增計數的那一行。
2. **Exporter 端**：postgres_exporter v0.20.1 送哪一條 SQL、怎麼把一列結果變成 metric 名稱與 label、哪些列被丟掉、預設有沒有開、要什麼權限。
3. **Metric**：最後的名稱與 label。
4. **Lab 觀察**：metric 有沒有真的出現在實驗裡、哪個情境讓它動了。

每個原始碼參考都用 `gh api` 取 tag 上的檔案，逐行核對過關鍵字。另外做了一次輕量檢查：開 `log_statement=all` 記下 exporter 兩次 scrape 送出的所有 SQL。<span class="at-chip at-ev-tested">實測</span>[^pg-trace-exp] Lab 欄的「實測」只用在親眼看到的情況；只讀過原始碼的標「讀碼」，推論標「推論」。兩個版本相同的行為只釘 17 的行號，有差異時兩邊都釘。

## 先講結論

1. **Exporter 送出的 SQL 和原始碼一致。**一次 scrape 的每一條語句都在 PostgreSQL log 裡，和 collector 檔案裡的常數相同；PG16 與 PG17 只差在 bgwriter 與 checkpointer 兩條（見[下一節](#sql)）。<span class="at-chip at-ev-tested">實測</span>[^pg-trace-exp]
2. **一個 exporter 用兩條連線，壞的時候表現不同。**舊架構（`pg_up`、`pg_stat_database_conflicts`）重用一條常駐連線；新架構（其他 `pg_*`）每次 scrape 開一條新連線、跑完就斷。log 裡兩次 scrape 的 collector 查詢來自兩個不同的 pid，舊架構的 pid 不變。所以「連線額滿」「帳號被鎖」時 `pg_up` 仍是 1，collector 結果整組消失。<span class="at-chip at-ev-tested">實測</span>[^pg-trace-ex-collect-setup][^pg-trace-ex-legacy-reuse][^pg-trace-exp][^pg-exp-target]
3. **NULL 幾乎都變成「series 不存在」，少數變成 0。**多數 collector 用 `sql.Null*` 讀值，NULL 就不輸出那條 metric 或整列跳過；但 `stats_reset`、`pg_postmaster_start_time`、`pg_locks` 的 count、long_running_transactions 的 age 把 NULL 換成 0，`pg_stat_activity` 則用 `COALESCE` 補 0。哪個是哪個見各表。<span class="at-chip at-ev-code">讀碼</span>
4. **很多 NULL 是權限造成的，不是錯誤。**`pg_stat_activity` 的 state、xact_start，`pg_stat_replication` 除了 pid 以外的欄位，`pg_stat_wal_receiver` 除了 pid 以外的欄位，在沒有 `pg_read_all_stats` 時都是 NULL；collector 照樣回報成功。只有 `pg_ls_waldir()` 是直接拒絕（wal collector 失敗）。<span class="at-chip at-ev-tested">實測</span>[^pg-src-activity-privs][^pg-src-walsnd-privs][^pg-src-walrcv-privs][^pg-trace-pg17-waldir-grant][^pg-exp-target]
5. **`pg_replication_lag_seconds` 在兩種斷線下結果不同，原因在 receiver 的起點。**receiver 只是斷線重連時，`pg_last_wal_receive_lsn()` 停在最後收到的位置，等於 replay 位置，lag 是 0；複本整個重啟後，receiver 起點被設成「當前 WAL segment 的開頭」，比 replay 位置小，lag 改成「距最後套用多久」。<span class="at-chip at-ev-code">讀碼</span>[^pg-trace-pg16-walrcv-flushinit][^pg-trace-pg16-walrcv-segstart][^pg-c-replication-lag]（行為本身是實測：0 與 103 秒[^pg-exp-target]；主頁與元件卡說的「receive_lsn 是 NULL」沒有被量過，和原始碼不符，見[沒有釘到原始碼行的部分](#unpinned)）
6. **crash recovery 丟棄統計，但 `stats_reset` 看不出來。**PostgreSQL 在控制檔不是正常關機狀態時呼叫 `pgstat_discard_stats()`；`stat_reset_timestamp` 沒有被設定，view 回 NULL，exporter 輸出 0。實驗中 `xact_commit` 6188 → 241，`stats_reset` 前後都是 0。<span class="at-chip at-ev-tested">實測</span>[^pg-trace-pg17-didcrash][^pg-src-crash-stats][^pg-trace-pg17-statsreset-null][^pg-trace-ex-db-statsreset][^pg-exp-target]
7. **`pg_locks_count` 不含 transactionid 鎖。**exporter 只數 `database IS NOT NULL` 的鎖；transactionid 鎖的 database 欄是 NULL，所以「等另一個交易的 row lock」不會出現在 `mode="sharelock"`。<span class="at-chip at-ev-code">讀碼</span>[^pg-trace-ex-locks-dbnotnull][^pg-trace-pg17-lock-xid-nulldb]

## Exporter 怎麼把一列變成 metric {#transform}

postgres_exporter v0.20.1 有兩套程式，處理方式不同。

| 步驟 | 新架構（collector 套件，大部分 `pg_*`） | 舊架構（exporter 套件：`pg_up`、`pg_exporter_*`、`pg_stat_database_conflicts`、queries.yaml） | 依據 |
|---|---|---|---|
| 連線 | 每次 scrape `sql.Open` 一個新的 pool（最多 1 條），先送 `SELECT version();`；失敗就記 "Error opening connection to database" 並直接 return，**連 `pg_scrape_collector_success` 都不輸出** | 依 DSN 快取一個 `Server`，每次 scrape 先 `Ping()`（log 裡是一條 `;`）再重用；Ping 失敗才重連 | [^pg-trace-ex-collect-setup][^pg-trace-ex-setup-open][^pg-trace-ex-setup-maxconn][^pg-trace-ex-version][^pg-trace-ex-collect-fail][^pg-trace-ex-legacy-reuse][^pg-trace-ex-legacy-ping] |
| 成敗 | 每個 collector 一條 `pg_scrape_collector_success{collector}`；所有 collector 共用同一條連線並行查詢 | 連不上才讓 `pg_up` = 0；查詢失敗只讓 `pg_exporter_last_scrape_error` = 1 | [^pg-trace-ex-success][^pg-trace-ex-legacy-connerr][^pg-trace-ex-legacy-up] |
| 查詢 | 每個 collector 寫死一條 SQL，部分依版本切換（見下一節） | `SELECT * FROM <namespace>;`，欄位依內建對照表決定是 label 還是 counter | [^pg-trace-ex-legacy-select][^pg-c-conflicts-legacy] |
| 名稱 | `pg_` + collector 名 + 欄位名，寫死在程式裡；counter 不一定有 `_total`（`pg_stat_database_xact_commit`、`pg_stat_archiver_failed_count` 沒有，`pg_stat_bgwriter_*_total` 有） | `pg_` + view 名 + `_` + 欄位名 | [^pg-trace-ex-db-name][^pg-trace-ex-archiver-name][^pg-trace-ex-bgwriter-req-name] |
| NULL | 依 collector 而定：多數 NULL 就不輸出那條（或整列跳過）；少數換成 0 | 依對照表 | 各表 |
| settings | 只取 `vartype` 是 bool、integer、real 的設定；`.`、`-` 換成 `_`；有單位時換算成 seconds 或 bytes 並加後綴，`-1` 保留原值 | — | [^pg-c-settings-query][^pg-trace-ex-settings-name][^pg-trace-ex-settings-unit][^pg-trace-ex-settings-minus1] |

## Exporter 實際送出的 SQL {#sql}

PostgreSQL 16.15 與 17.11 各一台（非 replica），exporter 帳號有 pg_monitor，另開 stat_wal_receiver、database_wraparound、postmaster、stat_checkpointer、long_running_transactions。<span class="at-chip at-ev-tested">實測</span>[^pg-trace-exp]

| 連線 | 一次 scrape 送出的 SQL | PG16 | PG17 |
|---|---|---|---|
| 舊架構常駐連線（兩次 scrape 同一個 pid） | `;`（Ping）、`SELECT version();`、`SELECT * FROM pg_stat_database_conflicts;` | 3 條 | 3 條 |
| 新架構（每次 scrape 新的 pid，跑完就 disconnection） | `SELECT version();` 加上每個 collector 一條（stat_wal_receiver 兩條：先查 `information_schema.columns` 有沒有 `flushed_lsn`） | 22 條 | 23 條 |

兩個版本的差別都來自版本判斷：

| Collector | PG16 送出 | PG17 送出 | 原始碼 |
|---|---|---|---|
| stat_bgwriter | `SELECT checkpoints_timed, checkpoints_req, checkpoint_write_time, ... FROM pg_stat_bgwriter;`（11 欄） | `SELECT buffers_clean, maxwritten_clean, buffers_alloc, stats_reset FROM pg_stat_bgwriter;` | [^pg-c-bgwriter-17][^pg-trace-ex-bgwriter-after17] |
| stat_checkpointer | **不送**；每次 scrape 記一條 WARN「not available on PostgreSQL < 17.0.0, skipping」，`pg_scrape_collector_success` 仍是 1 | `SELECT num_timed, num_requested, restartpoints_timed, ... FROM pg_stat_checkpointer;` | [^pg-c-checkpointer-17][^pg-trace-ex-checkpointer-skip][^pg-trace-ex-checkpointer-query] |

其他 collector 兩邊送的 SQL 相同，和原始碼常數一致：stat_activity[^pg-c-activity-query]、stat_database（`SELECT datid,datname,...,active_time FROM pg_stat_database;`，`active_time` 只在 14 以上加入）[^pg-trace-ex-db-query][^pg-trace-ex-db-active-gate]、replication[^pg-c-replication-lag]、stat_replication[^pg-c-statrep-query]、replication_slots（兩條）[^pg-trace-ex-slots-diff][^pg-c-slots-query]、stat_wal_receiver[^pg-trace-ex-walrecv-from]、stat_archiver[^pg-c-archiver-query]、database_wraparound[^pg-c-wraparound-query]、postmaster[^pg-c-postmaster-query]、locks[^pg-c-locks-query]、wal[^pg-c-wal-query]、settings[^pg-c-settings-query]、long_running_transactions[^pg-c-longtx-query]。

## 陷阱 {#pitfalls}

- **stat_wal_receiver 在沒有 slot 時整列不輸出。**PostgreSQL 在 `primary_slot_name` 沒設時把 `slot_name` 填 NULL，exporter 看到 NULL 就 `continue`。「複本沒有 receiver」的規則只能套在用 slot 的複本。依原始碼，`wal_receiver_create_temp_slot = on` 會讓 receiver 建一個 `pg_walreceiver_<pid>` 的暫時 slot 並寫回 `slotname`，這時應該有 series；沒有實測。<span class="at-chip at-ev-tested">實測</span>（沒有 slot 時消失）<span class="at-chip at-ev-inferred">推論</span>（暫時 slot）[^pg-trace-pg17-walrcv-slotnull][^pg-c-walrecv-slotnull][^pg-trace-pg17-walrcv-tempslot][^pg-exp-target]
- **`pg_replication_lag_seconds` 在 receiver 斷線時是 0。**斷線重連時 `flushedUpto` 不會被重設，仍等於 replay 位置；只有 receiver 第一次啟動（例如複本重啟）時才被設成 segment 開頭，lag 才會變成「距最後套用多久」。位元組延遲看主庫的 `pg_stat_replication_pg_wal_lsn_diff`，「有沒有在收」看那一列在不在。<span class="at-chip at-ev-tested">實測</span>（0 與 103 秒）<span class="at-chip at-ev-code">讀碼</span>（原因）[^pg-c-replication-lag][^pg-trace-pg16-walrcv-flushinit][^pg-exp-target]
- **slot lost 時保留量 series 消失。**PostgreSQL 把 `restart_lsn` 設成無效，`pg_wal_lsn_diff` 與 `safe_wal_size` 都是 NULL，exporter 不輸出；只剩 `wal_status{wal_status="lost"}`。`pg_wal_lsn_diff > X` 的規則在最嚴重的時候回傳空。<span class="at-chip at-ev-tested">實測</span>[^pg-trace-pg16-slot-invalidate][^pg-trace-pg17-slot-safenull][^pg-trace-ex-slots-diff-valid][^pg-exp-target]
- **`safe_wal_size_bytes` 在沒設 `max_slot_wal_keep_size` 時不存在。**預設 −1，PostgreSQL 回 NULL。exporter 另外輸出 `pg_settings_max_slot_wal_keep_size_bytes` = −1（`-1` 不換算）。<span class="at-chip at-ev-tested">實測</span>[^pg-trace-pg17-slot-safenull][^pg-trace-ex-settings-minus1][^pg-trace-exp]
- **17 的 checkpoint 規則要另開 collector。**stat_checkpointer 預設關，stat_bgwriter 在 17 只查 4 欄；沒開時兩組名稱都不存在，collector 仍回報成功。反過來在 16 打開 stat_checkpointer，每次 scrape 一條 WARN、success=1、沒有資料。<span class="at-chip at-ev-tested">實測</span>[^pg-c-checkpointer-default][^pg-trace-ex-checkpointer-skip][^pg-trace-ex-bgwriter-after17][^pg-trace-exp]
- **16 的複本 checkpoint 數包含 restartpoint。**16 在複本上把 restartpoint 算進 `checkpoints_req`／`checkpoints_timed`；17 分到 `restartpoints_*`。同一條「checkpoint 太頻繁」規則在升級前後對複本的意義不同。<span class="at-chip at-ev-code">讀碼</span>[^pg-trace-pg16-ckpt-req][^pg-trace-pg17-rstpt-req]
- **XID age 的名稱是 `_seconds`，值是交易數。**exporter 直接把 `age(datfrozenxid)` 的整數輸出，名稱寫成 `age_datfrozenxid_seconds`。門檻用交易數（例如 1e9），不要套時間單位。collector 預設關。<span class="at-chip at-ev-tested">實測</span>[^pg-trace-ex-wrap-name][^pg-trace-pg17-xid-age][^pg-exp-target]
- **crash 後 counter 歸零，`stats_reset` 不動。**偵測 crash recovery 用 `resets(pg_stat_database_xact_commit[...])`，不要用 `stats_reset` 或 `pg_postmaster_start_time_seconds`。`offset` 比較的規則在歸零時會誤判，用 `increase()`／`rate()`。<span class="at-chip at-ev-tested">實測</span>[^pg-trace-pg17-didcrash][^pg-trace-ex-db-statsreset][^pg-exp-target]
- **temp file 在檔案刪除時才計入。**長時間執行、還沒結束的排序不會讓 `temp_bytes` 增加；它反映的是「已經結束的」暫存檔。<span class="at-chip at-ev-code">讀碼</span>[^pg-trace-pg17-temp-call]
- **row lock 等待不在 `pg_locks_count` 的 `sharelock` 裡。**等待另一個交易的 row lock 時，真正在等的是那個交易 XID 上的 ShareLock（transactionid 鎖），`database` 是 NULL，被 exporter 排除；同時拿到的 tuple 鎖有 database 欄，應該會算在 `exclusivelock`（未實測）。等鎖的 session 數改看 `pg_stat_activity_count{wait_event_type="Lock"}`。<span class="at-chip at-ev-code">讀碼</span>（排除）<span class="at-chip at-ev-inferred">推論</span>（row lock 等待用 transactionid 鎖：PostgreSQL 文件的說法，未釘行號）[^pg-trace-ex-locks-dbnotnull][^pg-trace-pg17-lock-xid-nulldb]
- **沒有 pg_monitor 時，多數 collector「成功」但數字是 0 或沒有 series。**`pg_stat_activity_count` 少算別人的 session，`max_tx_duration` 是 0，stat_replication 沒有 diff，stat_wal_receiver 沒有 series。唯一會失敗的是 wal collector，可以當代理訊號。<span class="at-chip at-ev-tested">實測</span>[^pg-trace-pg17-activity-noperm][^pg-trace-pg17-waldir-grant][^pg-exp-target-raw]
- **`pg_stat_activity_count` 排除的只是 collector 自己那條連線。**舊架構的常駐連線（idle）照樣算進去；state 是 NULL 的背景程序不算。和 `pg_stat_database_numbackends` 不會相等。<span class="at-chip at-ev-code">讀碼</span>[^pg-trace-ex-activity-self][^pg-trace-ex-activity-join][^pg-trace-ex-legacy-reuse]

## 沒有釘到原始碼行的部分 {#unpinned}

| 說法 | 現在的依據 | 等級 |
|---|---|---|
| 複本重啟後 `pg_last_wal_receive_lsn()` 是 NULL（主頁 HA 一節、元件卡 silent_failures、`summary.txt` D2） | 實驗沒有查 `pg_last_wal_receive_lsn()`。原始碼顯示 receiver 一旦被要求啟動，`flushedUpto` 就被設成 segment 開頭，不是 0[^pg-trace-pg16-walrcv-flushinit][^pg-trace-pg17-receive-lsn-null]；兩種情況都會走 ELSE 分支，觀察到的 103 秒都解釋得通 | 讀碼與原說法不符；建議改寫 |
| crash recovery 丟棄統計在 13～15 也一樣（主頁、元件卡寫「13～17」） | 只核對了 16、17 的 StartupXLOG[^pg-trace-pg16-crash-stats][^pg-src-crash-stats]；13～15 沒有取檔 | 未驗證 |
| row lock 等待用的是 transactionid 上的 ShareLock | PostgreSQL 文件（Explicit Locking）；`heapam.c` 的 `XactLockTableWait` 沒有釘行號 | 推論 |
| `wal_receiver_create_temp_slot = on` 時 stat_wal_receiver 有 series | 讀碼（slot 名稱寫回共享記憶體[^pg-trace-pg17-walrcv-tempslot]）；沒有實測 | 推論 |
| archiver 在失敗後「休息約 60 秒」 | `PGARCH_AUTOWAKE_INTERVAL` 是 60 秒，但有新 WAL segment 時會被提早喚醒；實驗的 `increase()[1m]` 約 3 符合沒有新 segment 的情況 | 讀碼＋實測 |
| backend 統計最晚多久會出現在 view | 只讀到 `PGSTAT_MIN_INTERVAL` = 1 秒[^pg-trace-pg17-flush-interval]；閒置 backend 的 flush 時機沒有實測 | 讀碼 |
